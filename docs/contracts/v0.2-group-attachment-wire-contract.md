# v0.2 Group and Attachment Wire Contract

This document freezes the narrow wire surface used by AWiki Lite CLI v0.2. The authoritative
sources are the current Message Service validators and the P4/P7 API documents in the sibling
`message-service` repository.

## Capability Gate

Before a state-changing Group or Attachment workflow, call `anp.get_capabilities` through
`/im/rpc` with the current Device Access bearer. The response must contain a non-empty
`service_did`, `transport-protected`, and the exact required profiles/content types.

A read-only probe of `https://awiki.info/anp-im/rpc` on 2026-08-06 confirmed:

- profiles: `anp.group.base.v1`, `anp.attachment.v1`;
- security profile: `transport-protected`;
- content types: `text/plain`, `application/json`,
  `application/anp-attachment-manifest+json`;
- `limits.max_object_bytes = "1073741824"` and a non-empty `service_did`.

The real service DID is deliberately not stored in fixtures. Attachment v2, Group E2EE, MLS and
`object-e2ee` are outside this client version and must never be selected as fallback profiles.

## Ordinary Group

All standard requests use `/im/rpc`, `anp.group.base.v1` and `transport-protected`.
`group.create` targets `{kind: "service", did: capability.service_did}`. `group.get_info`,
`group.add` and `group.send` target the exact Group DID. State-changing requests carry
`anp-rfc9421-origin-proof-v1`; the proof is produced only by the ANP SDK.

The fixed create body uses a private `admin-add` group, standard owner/admin/member permissions,
attachments enabled, and a decimal-string maximum of 500 members. v0.2 `group.add` accepts only
`member_did` with role `member`. `group.send` accepts either `text/plain` or the standard attachment
Manifest type; message and operation IDs must survive exact retries.

Local reads use `anp.group.local.v1`: `group.list`, `group.list_members`, and
`group.list_messages`. Their cursors are opaque. `group.get_info` remains the standard Group Base
method and requests private policy/member data only with the current bearer.

## Plain Attachment

All four control methods use `anp.attachment.v1`, `transport-protected`, a service target, closed
`meta/body` shapes, and no separate origin proof. The idempotency scope is exactly sender DID,
target service DID, method, and operation ID.

The lifecycle is:

1. Allocate `attachment_id`; stream the regular file to determine decimal size and SHA-256
   base64url digest.
2. `attachment.create_slot` with `object_encryption_mode = "none"`, the exact target, MIME and
   filename.
3. PUT bytes to the returned HTTPS `upload_uri` using only validated upload headers and without
   redirects.
4. `attachment.commit_object` with the same size/digest. On an explicit pre-commit failure,
   attempt `attachment.abort_object`; an unknown result uses exact retry instead.
5. Send one `application/anp-attachment-manifest+json` Direct or Group Base message.

The Manifest contains one attachment, the committed `object_uri`, the same size/digest/MIME, and
`encryption_info.mode = "none"`. Download uses `attachment.get_download_ticket` with context copied
from an authenticated message projection. Exactly one of `message_target_did` and `group_did` is
present. Ticket and upload/commit credentials are secrets and never enter fixtures or logs.

## Closed Failure Boundary

Reject E2EE profiles, device selectors, Handle members, unknown content types, malformed/foreign
cursors, mismatched response IDs, redirects, non-HTTPS object endpoints, unsafe local files,
unknown upload headers, oversized objects, and size/digest mismatches. A 401 clears the local
session. Remote error messages and credential-bearing response bodies are never rendered.
